# 信息维护填写说明

本文档说明信息维护页面中三张表的字段顺序、必填项和校验规则。批量导入支持 `.xlsx` 和 `.csv`，第一行必须是模板中的完整表头。

## 通用规则

- 新增、修改、删除都需要提交审核，审核通过后才写入正式表。
- 批量导入只提交新增申请；如文件内主键重复，或与正式表已有主键重复，会被拒绝。
- 模板 xlsx 和模板 csv 只包含表头；需要下载现有数据请使用导出 xlsx 或导出 csv。
- 空白行会被忽略。

## 客户表

文件字段：

- `客户id`
- `名称`
- `资产`
- `月产出`
- `业务单位`
- `期货业务单位`
- `负责人`
- `客户经理`

填写约束：

- `客户id` 不能为空。
- `客户id` 只能是数字。
- 新增客户时，`客户id` 不能与已有客户重复。
- 修改客户时允许修改 `客户id`，但新 `客户id` 不能与其他已有客户重复。
- 客户 ID 修改审核通过后，正式服务器表中关联的 `客户id` 会同步改为新 ID，待审核中的相关服务器申请也会同步更新。
- `名称`、`资产`、`月产出`、`业务单位`、`期货业务单位`、`负责人`、`客户经理` 当前无额外格式校验，可按业务实际填写。
- `负责人` 是该客户的对接负责人；服务器信息表在「自动同步负责人」时按 `客户id` 关联本表的 `负责人` 字段取值。

## 机柜信息表

文件字段：

- `机房`
- `机柜`
- `机位`
- `瓦数(w)`
- `费用(年)`

填写约束：

- `机房` 不能为空。
- `机柜` 不能为空。
- `机房` + `机柜` 组合是机柜表主键，新增时不能与已有机柜重复。
- 修改机柜时不允许修改 `机房` 或 `机柜`。
- `机柜` 不限制命名格式，任意非空字符串均可。
- `机位` 格式应类似 9-10，即起始数字-结束数字。
- `瓦数(w)`、`费用(年)` 当前无额外格式校验。

## 服务器信息表

文件字段：

- `序列号`
- `品牌`
- `型号`
- `客户id`
- `客户名称`
- `负责人`
- `归属单位`
- `CPU型号`
- `网卡`
- `管理ip`
- `交易ip`
- `带外ip`
- `管理密码`
- `带外密码`
- `服务器成本(万)`
- `用途分类`
- `用途`
- `防火墙白名单`
- `资源申请编号`
- `是否液冷`
- `所在机房`
- `所属机柜`
- `所属机位`
- `上架时间`
- `接入行情`
- `接入柜台`
- `备注`

填写约束：

- `序列号` 不能为空。
- `序列号` 是服务器表主键，新增时不能与已有服务器重复。
- 修改服务器时不允许修改 `序列号`。
- `客户id` 不能为空。
- `客户id` 必须存在于客户表。
- `负责人` 存储于服务器表，可手动填写；表单中可用「自动同步负责人」按钮按 `客户id` 从客户表补充（大部分场景与客户表一致，个别场景可手动调整）。
- `所在机房` + `所属机柜` 必须存在于机柜信息表。
- `所属机柜` 不限制命名格式，但必须与机柜信息表中的机柜名称完全一致。
- `所属机位` 格式应类似 9-10，即起始数字-结束数字。
- `所属机位` 必须落在对应机柜登记的机位范围内。
- `所属机位` 不能与其他服务器已占用机位重叠。
- `管理ip`、`带外ip` 必须是有效 IPv4 地址或 IPv4 CIDR 地址（例如 10.71.141.193 或 10.71.141.193/25）；为空时不校验。
- `品牌`、`型号`、`CPU型号`、`网卡`、`服务器成本(万)`、`归属单位`、`用途分类`、`用途`、`防火墙白名单`、`资源申请编号`、`是否液冷`、`管理密码`、`带外密码`、`备注` 当前无额外格式校验。
- `上架时间` 只存日期（`YYYY-MM-DD`，如 `2026-10-29`），编辑表单里是日期选择控件；手工填 `2026/9/1`、`2026.9.1` 这类写法会自动归一成 `2026-09-01`。上下架请求经「机位IP分配 → 具体实施」落库时，该字段**自动填入请求提交日期**，不需要在上下架请求里填写；分配、实施两个阶段的表单里都可以改写，以最后一次提交为准；若在表单里被清空，则回落到请求提交日期（不会留空）。
- `备注` 为服务器表末列。上架请求（上下架请求）里填写的 `备注` 在「机位IP分配 → 具体实施」落库时会自动带入服务器记录，分配/实施表单里也可直接改写；服务器新增、修改表单可手工维护。
- `防火墙白名单`、`备注` 支持多行文本（换行符 `\n` 会原样保存）。在信息维护/审核页的编辑表单里这两个字段渲染为**可拖拽调整高度**的多行编辑框；导入导出仍按普通文本单元格处理（xlsx 中需开启「自动换行」才能完整显示多行）。

### 多值标签字段：用途分类 / 接入行情 / 接入柜台

这三个字段都是**多选标签**：`用途分类` 可以同时挂多个用途，`接入行情` / `接入柜台` 一个服务器可以同时接多个行情源 / 柜台。三者各有**独立的候选池**，互不影响。

- 编辑表单里是标签框：点一下展开候选标签，点选即加入；已选标签显示成小块，点 `×` 移除。候选里搜不到时可让管理人员在设置页新增。
- 存储格式是一条文本，多个标签用半角逗号加空格分隔，如 `CTP行情, Level-2`。导入导出、版本快照、审批流都按这列文本处理，Excel 里直接写 `CTP行情, Level-2` 也能被识别。
- 导入时中英文逗号、顿号、分号都认（`、` `，` `;` 都会被当分隔符），重复标签自动去重，最终统一写成 `A, B`。
- 单个标签最长 40 字；一条记录单字段最多 20 个标签。
- 候选标签只能由**管理人员**在「设置 → 字段标签管理」里新增 / 改名 / 删除；业务人员、机房人员只能选已有标签。
- 删除标签时，只要还有服务器记录或待审批申请在用，就会被拒绝（提示「只能改名」）。
- 改名会**级联刷新**：正式记录和待审批申请里的旧标签值一起换成新值。
- 直接改 Excel 或走 API 写入的新值，会在下次读取候选池时**自动收纳**进池（标记来源为「来自数据」），不会变成孤儿值。
- 接口：`GET /api/field-options?entity=servers` 读候选池（登录即可）；`POST/PATCH/DELETE /api/field-options` 维护，仅管理人员。
- `用途分类` 从单值改为多选时，**表头不变**，老值（如 `行情交易`）原样保留并自动收进 `用途分类` 的候选池，无需手工转换。
- 升级：只新增 SQLite 表 `field_options`，**不动任何 Excel 表头**，部署新代码后重启服务即可（`init_storage()` 自动建表），老数据无需转换。

## 上下架请求：请求类型

请求表单的「请求类型」决定走哪条流程：

| 请求类型 | 流程 | 实施完成后 |
|---|---|---|
| 上架 | 机位IP分配 → 具体实施 | 新增一条服务器记录 |
| 下架 | 直接进具体实施 | 服务器整行移入回收站，服务器表删掉该行 |
| 变更 | 直接进具体实施 | 以现有记录为底合并，改完直接写入正式表（序列号不可改） |

- 上架要求序列号**不在**服务器表里；下架 / 变更要求序列号**已存在**。
- 下架、变更请求的客户id / 所在机房在提交时会从服务器记录**自动补齐**；下架不允许改成别的客户/机房。
- 原来的「上下架需求」输入框已取消，需求请写进 `备注`（老数据里的「上下架需求」已在迁移时并入备注）。
- 请求表新增 `接入行情`、`接入柜台`，与服务器表共用同一个候选标签池。

## 回收站

下架实施完成后，服务器整行快照进入**回收站**（左侧导航「回收站」，仅管理人员可见）。

- 卡片展开后可直接改客户id / 所在机房 / 所属机柜 / 所属机位，再点「重新上架」。
- 重新上架会走完整校验：客户必须已登记、机柜与机位必须在机柜表范围内、机位与 IP 不得被占用。冲突时报错并保留回收站记录——先补登客户或腾出机位，再来恢复。
- 「永久删除」会连带删除该序列号的全部资料附件（数据库记录 + `data/archive/<序列号>/` 文件），**不可恢复**。
- 回收站不能手工改 Excel 维护，只能走页面或接口：`GET /api/trash`、`POST /api/trash/<id>/restore`、`DELETE /api/trash/<id>`。

## 服务器资料（附件）

资料按 `序列号` 归属，**不是表格列**，因此**不参与导入、导出、模板和版本快照**（导出的 xlsx/csv 里不会有资料）。

- 上传入口共四处，看到的是同一份档案：上下架请求表单（随请求一并上传）、上下架请求卡片、审核管理的「服务器机位ip分配 / 具体实施」卡片、信息维护-服务器信息表的操作列「资料」按钮。
- 一次可以选择多个文件上传；上架请求经「机位IP分配 → 具体实施」落库成服务器记录后，服务器表自动继承该序列号下的资料，无需重新上传。
- 「重命名」只改资料名称（下载时的文件名），文件内容不变；「删除」会同时删除磁盘文件，不可恢复。
- 文件保存在服务器 `data/archive/<序列号>/` 目录下，元数据在 `data/app.db` 的 `attachments` 表中。单次上传体积上限由 `app.ini` 的 `max_upload_mb` 控制（默认 64MB）。
- 设置页的「手动备份」只备份三张正式表、`app.db` 与 `users.json`，**不含 `data/archive`**；需要完整灾备时请自行归档该目录。
- 权限：上传要求具备「提交上下架请求」或「审核上下架请求」权限，且该序列号在自己可见范围内；重命名 / 删除限管理人员、上传者本人、以及该服务器所属机房的机房人员。

### 已有环境如何升级

资料功能只改数据库和目录，**不动任何 Excel 表头**，所以老数据不需要转换。

- 直接部署最新代码并重启服务即可：启动时 `init_storage()` 会自动建 `attachments` 表、索引和 `data/archive` 目录，无需手工迁移。
- 想先改库、暂不重启，或想在动库前留一份快照，可手工执行（在项目根目录，用跑服务的那个 python）：

```bash
python scripts/add_attachments_table.py --dry-run     # 只看现状与将执行的改动
python scripts/add_attachments_table.py               # 真的改（会先备份 app.db 到 data/migration-backups/）
```

- 脚本幂等，重复执行只会输出「已就绪」；若 `data/archive` 由 root 创建而服务以其它用户运行，用 `--owner www-data:www-data`（或事后 `chown`）修正属主，否则上传会失败。
- 单次上传上限默认 64MB，需要更大时在 `app.ini` 的 `[app]` 段加 `max_upload_mb = 128`（不要超过反向代理的 `client_max_body_size`）。

### 从「是否上架」升级到「请求类型」

新代码**只认「请求类型」**，不保留「是否上架」的兼容分支，所以旧库必须先用脚本适配一次（脚本幂等，重复跑只会输出「已就绪」）：

```bash
python scripts/migrate_rack_request_types.py --dry-run   # 先看会改哪几条
python scripts/migrate_rack_request_types.py             # 真的改（先备份 app.db 到 data/migration-backups/）
```

脚本做三件事：

1. `rack_requests.request_data` 里的 `是否上架`（是/否）转成 `请求类型`（上架/下架），`上下架需求` 并入 `备注`，补齐 `接入行情` / `接入柜台`，再按新表头顺序重建整条 JSON；
2. 建 `trash` 表（回收站）；
3. 把服务器表里 `用途分类` / `接入行情` / `接入柜台` 已出现的值收进候选标签池（`source=data`）。

脚本不动任何 Excel 表头；写入后会回读校验，任何一条不符即退出码 2 并提示用备份回滚。

## API Token

Token 用于通过接口 / MCP 工具访问本系统，**只能由本人自助生成**，不需要手工编辑 `users.json`，也不由管理员代发。

- **入口**：左下角钥匙图标 →「🔑 获取 Token」。没有 token 时点「生成 Token」；已有时可查看完整值、复制，或「重新生成」。
- 生成规则：`secrets.token_urlsafe(32)`，43 个字符，只含 `A-Z a-z 0-9 _ -`，可直接放进 `Authorization: Bearer <token>`、URL 和配置文件，无需转义。
- **一个用户只有一枚 token**：重新生成会**立即让旧 token 失效**，正在使用它的 MCP / 脚本会立刻收到 401，需要同步更新配置。
- **必须登录页面才能生成/重置**：用 token（`Authorization: Bearer`）调用 `/api/my-token/regenerate` 会被拒绝（403），避免一枚泄露的 token 把本人挤掉。
- Token 保存在 `data/users.json` 的 `api_token` 字段，随文件持久化，重启服务不失效；手动备份（设置页）会一并备份该文件。
- **管理员既看不到也改不了他人的 token**：用户表接口不下发 `api_token`，设置页没有 token 列，也没有代生成按钮；保存用户配置时 token 一律保留磁盘原值，改不动也抹不掉。某人 token 需要更换时，由他自己重新生成。
- Token 等同于该账号的密码，权限与该账号完全一致（管理人员 token 的写操作会直接生效、免审批）。不要提交到代码库，也不要放在多人共用的机器上。

## 接入 MCP（让 agent 直接操作本系统）

`mcp_server/` 里是一个 stdio MCP server，**同一份代码同时支持 Claude Code CLI 与 WorkBuddy 桌面/CLI**，零第三方依赖（只用 Python 标准库）。

**拿代码**：页面左下角钥匙按钮 →「⬇ 下载 MCP」，得到 `server_management_mcp.zip`。这个包由后端**实时从 `mcp_server/` 打包**，所以下载到的永远等于当前线上代码（不会出现「下载的包里没有某个新工具」）；解压后顶层目录是 `server_management_mcp/`。

```bash
# 1) 先拿到自己的 token（页面左下角钥匙 →「获取 Token」）

# 2) 一条命令注册到本机 host（--host claude / workbuddy / both）
python server_management_mcp/install_config.py --host both \
  --base-url http://127.0.0.1:18888 \
  --token <你的 token>

# 3) 先 dry-run 看要写什么
python server_management_mcp/install_config.py --host both --base-url ... --token ... --dry-run
```

- 注册脚本会**先备份** `~/.claude.json` 或 `~/.workbuddy/mcp.json`，只增改 `server-management` 一项，不动其他配置。
- WorkBuddy 侧**不会自动生效**：打开连接器管理页 → 右上角「自定义连接器」→ 对新条目点**信任**，再新开会话。
- 一个 MCP 进程 = 一枚 token = 一个账号，权限与该账号完全相同；**不支持**在参数里声明身份。
- agent 每次会话先调 `sm_bootstrap`，它从 `/api/skill/{manifest,docs,schema}` 实时拉取当前 skill 正文与字段清单——**所以新增字段后只要重启后端，agent 立刻能看到，不用重新分发 skill**。
- 只读端点默认免鉴权（只暴露文档与字段名）；需要收紧就在 `app.ini` 配 `skill_docs_token`。
- 只有装 MCP 这一步需要人工；之后 agent 拿到的字段永远等于当前实现。详细配置与排查见 `mcp_server/README.md`。
